# Кодовая система QenTerra

## Назначение и границы

Этот справочник задаёт общую инженерную семантику для нативных приложений, сайтов, браузерных расширений и инструментов. Он дополняет `MASTER_RU.md`; платформенные конвенции и архитектура продукта остаются источником истины в своих границах. Перед реализацией или ревью прочитайте этот документ, профиль языка, архитектуру продукта и конфигурацию-источник истины.

Качество кода — свойство продукта: код, который работает, но небезопасен для изменения разработчиком, впервые открывшим модуль, лишь отложил свою цену.

## Кодовое ядро

### Владение и границы

- У каждого изменяемого значения один объявленный источник истины; generated output не редактируется вручную.
- Модуль владеет одной доменной ответственностью и узким публичным интерфейсом. `Manager`, `Helpers`, `Common` и `Utils` требуют точной доменной роли.
- Presentation не владеет persistence, network I/O или business policy; инфраструктура не знает деталей рендеринга экрана.
- Направление зависимостей явное. Код попадает в общий слой семьи только после двух реальных потребителей с одинаковой семантической потребностью.

### Именование и публичные API

- Типы и значения используют точные существительные; операции — глаголы результата. `saveProfileChanges` лучше `handleSubmit`, `ArtworkCache` лучше `DataManager`.
- Публичный API делает понятными результат, эффекты, предусловия, отказ и lifecycle в месте вызова или в короткой документации.
- Boolean-параметр, меняющий смысл, заменяется именованной опцией, типом состояния или отдельной операцией. Сокращения допустимы, только если стандартны для платформы или домена.

### Состояние, эффекты и ошибки

- Представляйте доменное состояние явными вариантами и допустимыми переходами, а не неограниченным набором Boolean-флагов.
- Network, filesystem, storage, разрушительные действия, permissions, telemetry и пользовательские уведомления находятся на явной границе системы.
- Ошибка сохраняет полезный контекст. Пользовательская ошибка называет случившееся, безопасный остаток и следующее безопасное действие, не раскрывая диагностику или секреты.
- Моделируйте отмену, повтор, частичное завершение и восстановление, когда операция имеет такие состояния.

### Читаемость и локальная структура

- Начинайте файл с публичного сценария и назначения, детали оставляйте ниже.
- В блоке один уровень абстракции: не смешивайте orchestration, policy, parsing, persistence и rendering просто из-за соседства.
- Делайте success path читаемым; guard clauses допустимы, если уменьшают вложенность и не скрывают cleanup.
- Давайте сложным предикатам, преобразованиям и эффектам имена. Компактность никогда не важнее ясности.
- Formatter владеет синтаксическими пробелами и переносами; пустые строки разделяют только логические шаги.
- Комментарии объясняют намерение, ограничения, компромиссы или внешний контракт, но не очевидные строки и не устаревшую историю.
- Выделяйте повтор только после появления реального общего понятия.

### Проверка и приватность

- Изменение поведения получает достоверное regression coverage или явно называет требуемую live/manual приёмку.
- Тесты описывают поведение и результат, а не приватную последовательность реализации.
- Изменения permissions, storage, network, retention, dependencies, generated sources, публичных API или разрушительного поведения обновляют документацию и доказательства.
- Автор понимает поведение и границы, удаляет мёртвые ветки и неиспользуемые зависимости и прикладывает обычные доказательства проверки.

## Понятный человеку код

Код понятен, когда разработчик, не писавший модуль, может безопасно его изменить. По файлу и ближайшим контрактам ревьюер должен видеть ответственность, использование и результат, зависимости и эффекты, состояния и ошибки, путь проверки.

Вопрос ревью: **сможет ли разработчик, впервые открывший модуль, безопасно внести нужное изменение без экскурсии по всему репозиторию?** Если нет, улучшите границу, имя, документацию, локальную структуру или тест до расширения фичи.

## Устройство файлов и модулей

- Размещайте одну публичную ответственность в файле или небольшой папке. Разделяйте файл, когда накопились независимые причины для изменений, а не по произвольному числу строк.
- Держите constructors и public entry points рядом с создаваемыми типами. Private parsing, mapping, persistence и rendering helpers размещайте рядом с владельцем.
- Импортируйте только прямые зависимости. Facade может давать стабильную public surface, но не скрывает cycles или global mutable state.
- Удаляйте dead code, закомментированные реализации, неиспользуемые flags и compatibility branches после конца support window.

## Оформление кода и примеров

- Доверьте whitespace formatter репозитория. Не выравнивайте код вручную так, чтобы следующая смена имени разрушила раскладку.
- Переносите expressions по смысловым границам: arguments, collection entries, chained stages и Boolean clauses.
- Пример кода содержит imports, input, expected result, failure behavior и запускающую команду, когда эти детали влияют на использование.
- Небольшой законченный пример лучше большого фрагмента с отсутствующими types. Помечайте illustrative pseudocode как pseudocode.
- Logs, IDs, paths, commands и machine output используют monospace. UI labels и обычный текст его не используют.

## Generated, vendored и migrated code

- Generated files называют generator, а каноническая команда проверки отклоняет ручной drift.
- Vendored code сохраняет upstream source, version, license, local modifications и update procedure.
- Migration отделяет mechanical transformation от behavior changes. До массового применения проверьте повторяемость transform.
- Compatibility code называет условие удаления. Постоянная папка `legacy` является немаркированным продуктовым решением, а не migration plan.

## Профили языков

### Swift и нативные платформы Apple

- Следуйте Swift API Design Guidelines: ясность в месте вызова, осмысленные argument labels и документация, выявляющая недостатки API.
- Используйте принятые formatter и linter; совместимый migration formatter допустим только при идемпотентном проверяемом output.
- Явно задавайте concurrency isolation через `@MainActor`, actors, `Sendable` и ownership на границах API.
- SwiftUI views показывают state и делегируют policy, persistence, network и долгие операции ограниченным collaborators.
- Blocking: formatter, lint, build, unit tests. Нативный рендеринг, VoiceOver, permissions, audio, filesystem и hardware — live/manual evidence.

### TypeScript, web и браузерные расширения

- Используйте strict TypeScript. Внешняя граница с `any` изолируется и сразу сужается или валидируется.
- Представляйте состояние discriminated unions или эквивалентными явными типами.
- DOM, extension messaging, storage и network API находятся за узкими адаптерами.
- Blocking: Prettier, ESLint, строгая type checking, unit tests и browser/E2E evidence, нужные продукту.

### Инструменты Python и Bash

- Python использует Ruff, type hints на публичных границах и pytest.
- Bash безопасен для повтора, экранирует Unicode- и spaced paths, явно обрабатывает ошибки и не применяет неразрешённые glob или широкие пути для разрушительных действий.
- Ruff/pytest и ShellCheck/shfmt advisory до scoped adoption продукта, затем blocking в его канонической команде.

## Принуждение и доказательства

| Класс | Примеры | Режим |
| --- | --- | --- |
| Механическое | Format, lint, typecheck/build, unit tests, generated drift, raw-token guard | Blocking в принятом профиле |
| Высокая цена | Публичный API, dependency, storage/network boundary, migration, exception | Запись в PR; ADR для нормативного или межпродуктового решения |
| Архитектурный риск | Complexity, дублирование, рост файла, цикл зависимостей | Отчёт с владельцем и датой пересмотра |
| Живая граница | Нативный рендеринг, VoiceOver, browser runtime, permissions, hardware, сервис | Live evidence или manual gap |

Каждый репозиторий документирует одну каноническую команду проверки, покрывающую blocking checks принятого профиля.

## Контракт для контрибьюторов репозитория

Каждый репозиторий хранит короткие продуктовые правила в `CONTRIBUTING.md`, карту модулей и эффектов в `docs/ARCHITECTURE.md` и prompts доказательств в pull-request template. Design System Code System канонична; репозитории не копируют её целиком и не дают копиям разойтись.

## Исключения

Исключение фиксирует точное правило и путь, техническую причину, владельца, условие и дату пересмотра. Оно не меняет молча foundation, platform или product contract и не отменяет доказательства security, privacy, accessibility или разрушительной операции.

## Порядок внедрения

1. Добавьте нужный профиль и каноническую команду в один продукт.
2. Проведите audit текущих конвенций и зафиксируйте только реальные исключения.
3. Сделайте механические проверки blocking после чистой scoped migration.
4. Разделяйте behavioral, architecture, live и manual evidence.
5. Внедряйте систему в остальные продукты отдельными задачами; не смешивайте массовое форматирование с функциональной работой.
