# Стандарт документации репозиториев

Этот модуль определяет универсальную структуру публичной документации, проверку фактов и границы между пользовательскими материалами, contributor-документацией и внутренней рабочей историей. Продуктовые утверждения всегда сверяются с текущим кодом, разрешениями, хранилищем, зависимостями и фактическими release-артефактами.

## Принципы

1. **Один каркас, разные продуктовые факты.** README используют общую информационную архитектуру, но установка, разрешения, приватность и распространение соответствуют типу продукта.
2. **Путь пользователя раньше деталей реализации.** Сначала объясните назначение, текущий статус и способ начала работы, затем архитектуру.
3. **Только проверенные утверждения.** До описания приватности и совместимости прочитайте manifests, entitlements, network clients, storage code, dependency metadata и release archives.
4. **Публичная документация — не чердак.** Завершённые планы, agent output, remediation briefs, private runbooks и история реализации не входят в публичное дерево.
5. **Честные пробелы входят в статус продукта.** Автоматические проверки, живая приёмка и оставшаяся ручная проверка сообщаются отдельно.
6. **Шаблон — одноразовый каркас.** Неиспользуемые секции удаляются, а не остаются пустыми или заполненными общей водой.

## Канонические корневые файлы

| Файл | Правило |
| --- | --- |
| `README.md` | Обязателен. Назначение, статус, интерфейс, начало работы, разработка, ограничения и карта документов. |
| `LICENSE` | Обязателен для публичного source-репозитория. Публикуется только явно выбранная лицензия с корректным правообладателем. |
| `CHANGELOG.md` | Обязателен для версионируемого или release-oriented продукта. Keep a Changelog и Semantic Versioning применяются только там, где соответствуют реальному процессу. |
| `CONTRIBUTING.md` | Рекомендуется. Setup, проверки, privacy-правила и требования к pull request должны быть специфичны проекту. |
| `PRIVACY.md` | Обязателен при работе с пользовательскими данными, внешними сервисами, широкими разрешениями, аккаунтами, медиа, историей или локальным хранением. |
| `SECURITY.md` | Обязателен. Поддерживаемые версии, приватный канал сообщения, правила очистки доказательств и security boundaries. |
| `TERMS_OF_USE.md` | Рекомендуется для пользовательских продуктов; обязателен при внешних сервисах, пользовательском контенте, загрузках или чувствительных возможностях. |
| `THIRD_PARTY_NOTICES.md` | Обязателен, когда runtime включает или загружает сторонний код, модели, шрифты, медиа или другие лицензируемые компоненты. |
| `.github/FUNDING.yml` | Используется для публичных продуктов QenTerra только после явного решения о funding surface. |

`CODE_OF_CONDUCT.md`, `SUPPORT.md` и дополнительные funding-файлы необязательны. Добавляйте их только при наличии реальной политики или канала поддержки.

## Информационная архитектура README

Оба базовых профиля используют этот порядок:

1. Hero: иконка, название, одна строка назначения, правдивые badges и короткая навигация.
2. Краткое описание и заметный статус распространения.
3. Interface: реальный собранный UI на изолированных синтетических данных.
4. Возможности, сгруппированные по пользовательским задачам.
5. Начало работы: установка опубликованного продукта или сборка source-only продукта.
6. How it works только там, где поток данных объясняет безопасность, приватность или ограничения.
7. Разрешения и приватность: связь capability с целью и ссылки на полные политики.
8. Разработка: воспроизводимый setup и одна каноническая команда проверки.
9. Короткая архитектура или структура проекта со ссылкой на подробности.
10. Текущие ограничения и непроверенные границы.
11. Индекс документации.
12. Contributing, support и license.

README — карта, а не вторая копия каждого руководства. Полные build steps, обновление зависимостей, troubleshooting и release runbooks живут в отдельных документах.

## Качество кода

Каждый репозиторий принимает нужный языковой профиль QDS Code System и называет одну каноническую команду проверки. Код остаётся понятным разработчику, впервые открывшему модуль: его роль, зависимости, эффекты, ошибки и путь проверки видны через границы, имена, тесты или короткие комментарии. UI, domain policy, storage, network и platform effects остаются на явных границах. Не смешивайте несвязанное форматирование с изменением поведения.

Исключение из правила фиксирует точные правило и путь, техническую причину, владельца и дату пересмотра. Pull request разделяет automated checks, live checks и manual gaps; зелёная статическая проверка не заменяет реальную платформенную границу.

## Техническая документация

Простым репозиториям не нужно искусственно раздувать `docs/`, но нетривиальные проекты обычно предоставляют:

| Файл | Назначение |
| --- | --- |
| `docs/README.md` | Индекс публичной документации и карта аудиторий. |
| `docs/BUILDING.md` | Чистый checkout, источники истины, сборка, проверка и только локальные пути. |
| `docs/ARCHITECTURE.md` | Runtime flow, границы компонентов, persistence, concurrency, security и generation rules. |
| `docs/DEPENDENCIES.md` | Runtime и development dependencies, version policy, лицензии, источники и обновление. |
| `docs/TROUBLESHOOTING.md` | Восстановление от симптома без ослабления security или integrity checks. |

Публичный design/brand-документ допустим, если он нужен contributor. Implementation plans и завершённые remediation specifications остаются во временной рабочей области или приватной базе знаний.

## GitHub Wiki

Нативная GitHub Wiki служит пользовательским слоем только когда у продукта действительно есть опубликованный Wiki remote. Общее ядро: `Home.md`, `_Sidebar.md`, `Getting-Started.md`, `Feature-Overview.md`, `Privacy-and-Security.md` и `Troubleshooting.md`. Sidebar группирует страницы в порядке `Use`, `Understand`, `Build`, `Policies`.

Wiki не копирует legal-файлы и полные contributor guides, а ссылается на канонические версии основного репозитория. Изображения хранятся один раз в `docs/images/` и встраиваются абсолютными raw GitHub URLs. Funding не переносится в Wiki автоматически.

## Именование и стиль

- Repository-authored документация по умолчанию пишется на английском, если продукт не определил другую политику локализации.
- Заголовки используют sentence case.
- Имена политик согласованы: `Privacy Policy`, `Security Policy`, `Terms of Use`, `Third-party notices`.
- Даты записываются в ISO-формате: `YYYY-MM-DD`.
- Во всех репозиториях используются `THIRD_PARTY_NOTICES.md` и `TERMS_OF_USE.md`.
- Для внутренних файлов используются относительные ссылки и содержательный alt-текст.
- Shell-примеры помечаются `sh`, если синтаксис не требует Bash.
- Текст прямой и фактический: без неподтверждённых превосходных степеней, roadmap promises, fake metrics и пустых badges.
- Source-only, unsigned, unnotarized, prerelease или store-review статус показывается рядом с началом README.
- Иконка продукта визуально отображается в согласованном размере, а порядок badges остаётся семейным только при наличии реальных целей ссылок.

## Проверка источников приватности и legal

Перед изменением legal-документов проверьте:

- entitlements приложения или permissions расширения;
- network clients, внешние сервисы и явные действия открытия браузера;
- локальные пути хранения, retention, удаление и account actions;
- runtime, downloaded, bundled и build-only dependencies;
- лицензии моделей, медиа, шрифтов и website scripts;
- release archives, а не только source manifests.

Не утверждайте, что данные «никогда не покидают устройство», если системная синхронизация или обязательный внешний сервис может их обрабатывать. Назовите эту границу.

## Защита от рассинхронизации

Каноническая команда проверки каждого репозитория должна как минимум контролировать:

- разрешение локальных Markdown/HTML-ссылок;
- отсутствие незаменённых маркеров шаблона вне каталога шаблонов;
- согласованность README version, security support, archive names и changelog с источником версии;
- наличие каждой прямой runtime dependency в `THIRD_PARTY_NOTICES.md`;
- отражение permissions/entitlements в privacy-документации;
- существование referenced screenshots в `docs/images/`;
- отсутствие внутренних plan directories, AI working files и machine-specific paths в публичном дереве;
- корректность Funding YAML, если funding включён;
- покрытие Wiki sidebar-ом и корректные internal links, если Wiki опубликована.

Синтетические test paths и маленькие product icons требуют узких allowlists. Валидатор с постоянными false positives быстро превращается в декорацию, а декорации редко спасают релиз.

## Синхронизация изменений

| Изменение | Документы для проверки |
| --- | --- |
| Видимое пользователю поведение | README, changelog, screenshots, troubleshooting |
| Permission, entitlement, network, storage или retention | README, privacy, security, terms |
| Dependency или model | dependency guide, notices, license texts, build guide |
| Поддерживаемая ОС, browser, IDE или toolchain | README, building, contributing, CI |
| Distribution или release status | README, changelog, security support table, release links |
| Architecture или persistence boundary | architecture, security, contributing source-of-truth rules |
| Новый внешний сервис | README, privacy, terms, security и notices, если применимо |

## Словарь проверки

Используйте эти обозначения последовательно:

- **Automated:** lint, format, unit tests, builds, link, manifest и package checks.
- **Rendered:** визуально просмотренные screenshots или сгенерированные страницы.
- **Live:** сценарий выполнен в собранном продукте с реальной границей ОС или сервиса.
- **Manual gap:** ещё требуется hardware, account, permission, accessibility, visual, store или external-service acceptance.

Не сжимайте эти категории в слово «tested». Оно звучит бодро, но обычно прячет самую полезную половину фактов.

## Применение шаблонов

1. Выберите профиль README по типу продукта.
2. Скопируйте только нужные root, technical, GitHub и Wiki templates.
3. Замените каждый допустимый placeholder и удалите неприменимые optional sections.
4. Сверьте product, privacy, permission, dependency, version и support claims с кодом и build metadata.
5. Добавьте document checks в нормальную команду проверки проекта.
6. Откройте screenshots визуально: link checks не читают текст, нарисованный в пикселях.
7. Для native Wiki отдельно проверьте branch/SHA до правки и published read-back после push.

Шаблоны помогают не забыть структуру, но не являются legal advice и не заменяют факты продукта.
